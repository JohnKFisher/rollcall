# Roll Call 1.3 — App Intents / Quick Game Day adversarial audit

**Date:** 2026-09-23  
**Scope:** Investigation of the current working tree only. No production code, tests, settings, or build numbers changed.  
**Release judgment:** One source-proven navigation failure warrants a **BLOCKER** until resolved or explicitly accepted for 1.3. The control handoff, saved Shortcut entity resolution, and Release/device behavior still need end-to-end evidence. A passing unit test or simulator launch does not close those gaps.

## Classification and evidence standard

- **BLOCKER:** A demonstrated path can report Quick Game Day as handled while failing its core promise to show Game Day in a supported app state.
- **IMPORTANT:** A credible user-visible correctness or release risk that needs correction or targeted device evidence before acceptance.
- **PRE-EXISTING:** A behavior or limitation already present outside Quick Game Day that affects this entry path; preserve its context when testing.
- **DEFER:** A bounded edge or improvement that does not presently justify holding 1.3, provided the main release gate passes.

“Source-proven” means the stated behavior follows from the present code. “Device-unproven” means the source supports a risk but does not establish how iOS will execute the system entry path. This audit did not invoke a physical Action Button, Lock Screen control, Control Center control, Siri/Spotlight action, or a Release-installed Shortcut. It did not run an Xcode build or tests because this investigation must leave build numbers and all files other than this report untouched. The repository already contained unrelated modified and untracked files at the start of this audit; they were not changed here.

## End-to-end trace

| Entry | Handoff | App-side outcome |
| --- | --- | --- |
| Shortcuts / App Shortcut, and system discovery where offered | `OpenGameDayIntent` has an optional `GameDayTeamEntity`, `openAppWhenRun = true`, and iOS 26 foreground-immediate mode. `perform()` puts an ID or nil in the app-process `OpenGameDayRequestCenter`. See [QuickGameDay.swift](../../RollCall/QuickGameDay.swift#L68-L128). | `RootView` observes the request and calls `AppModel.resolveOpenGameDay`. |
| Control Center / Lock Screen / Action Button control on iOS 18+ | `ControlWidgetButton` runs `OpenGameDayControlIntent` in the extension; it returns an `OpensIntent` containing `OpenGameDayFromControlIntent`. The second intent has `openAppWhenRun = true` and submits a request with no explicit team. See [QuickGameDayControl.swift](../../RollCallControls/QuickGameDayControl.swift#L4-L26) and [QuickGameDayControlIntent.swift](../../RollCall/QuickGameDayControlIntent.swift#L58-L80). | The request exists only in the second intent's process memory. Successful navigation depends on that intent actually running in the app process and the root view handling it. |
| Direct `rollcall://game-day` URL, including an optional `team` UUID | `RootView.onOpenURL` parses the URL and submits a request. No current control or App Shortcut calls the URL builder; it is a separate route, not proof of the current control handoff. See [QuickGameDay.swift](../../RollCall/QuickGameDay.swift#L40-L65) and [RootView.swift](../../RollCall/RootView.swift#L864-L877). | Same resolver once the normal root content is mounted. |

The app target owns the team entity/query, resolver, and Shortcuts intent. The shared control-intent source is compiled into both the app and iOS 18 extension; the app itself retains an iOS 17 deployment target and embeds the extension in both Debug and Release configurations ([project.pbxproj](../../RollCall.xcodeproj/project.pbxproj)). The extension does not read teams or use an app group. The app reads its own `Application Support/RollCall/state.json` for Shortcuts entity lookup ([Models.swift](../../RollCall/Models.swift#L1665-L1682)). Apple's documentation says a widget intent with `openAppWhenRun = true` executes in the app process, which supports the intended second-stage design, while Apple's control-specific guidance describes a direct shared `OpenIntent`; the current two-stage behavior still needs device proof ([widget process guidance](https://developer.apple.com/documentation/widgetkit/adding-interactivity-to-widgets-and-live-activities), [control launch guidance](https://developer.apple.com/documentation/widgetkit/creating-controls-to-perform-actions-across-the-system)).

Once a request is visible, `RootView` waits for initial launch work, defers while blocking presentations exist, resolves against `AppModel.state`, changes `selectedTab`, and consumes the request ([RootView.swift](../../RollCall/RootView.swift#L815-L835), [RootView.swift](../../RollCall/RootView.swift#L880-L903)). An explicit ID wins; otherwise the last intentionally entered Game Day team wins. Neither selected-team browsing nor team count chooses a default. A missing remembered ID is cleared, and removing a team clears its remembered ID ([QuickGameDay.swift](../../RollCall/QuickGameDay.swift#L21-L37), [AppModel.swift](../../RollCall/AppModel.swift#L1211-L1245), [AppModel.swift](../../RollCall/AppModel.swift#L1347-L1367)).

## Findings

### B1 — BLOCKER — A valid request is consumed behind the manual Setup Guide

**Source-proven.** With at least one team and a remembered Game Day team, tap **Open Setup Guide** in Settings, then invoke Quick Game Day through a control or Shortcut. `beginSetupGuide()` sets `onboarding.activeFlow = .manualChooser`; therefore `shouldShowOnboarding` remains true even though teams exist ([RootView.swift](../../RollCall/RootView.swift#L2262-L2275), [AppModel.swift](../../RollCall/AppModel.swift#L1129-L1155)). The Quick Game Day handler checks modal flags but does not check the onboarding branch. It resolves the valid team, sets `selectedTab = .gameDay`, records `quickGameDayReached`, and consumes the request ([RootView.swift](../../RollCall/RootView.swift#L880-L903)). The visible `rootContent` renders onboarding instead of `mainTabs` while `shouldShowOnboarding` is true ([RootView.swift](../../RollCall/RootView.swift#L1303-L1329)). On a fresh scene `hasEnteredOnboardingFlow` starts false, so this can show the onboarding welcome view. The request cannot retry because it has been consumed. Later dismissal of the Setup Guide can reveal the previously selected Game Day tab, which makes the navigation delayed and surprising.

This is a concrete false-success path, including false `reached` telemetry; the system intent itself returns an empty successful result. It does not require an extension-process failure. Verify with an existing remembered team and with an explicit team; also repeat after terminating the app while manual Setup Guide state is persisted. Acceptance requires the invocation to visibly reach the intended destination or explicitly preserve/report the pending request until it can.

### I1 — IMPORTANT — A deleted explicit Shortcut team may fail before the app-owned fallback

**Source-supported; actual Shortcuts result device-unproven.** A saved Shortcut binds a team entity by UUID. `GameDayTeamEntityQuery.entities(for:)` reads `state.json` and omits IDs no longer in `state.teams` ([QuickGameDay.swift](../../RollCall/QuickGameDay.swift#L80-L94)). Apple's entity-query contract says missing IDs should be omitted, and entity queries participate in parameter resolution *before* `perform()` ([EntityQuery](https://developer.apple.com/documentation/appintents/entityquery), [entity queries](https://developer.apple.com/documentation/appintents/entity-queries)). Thus a deleted explicit team can be rejected or prompted by the system before `OpenGameDayIntent.perform()` submits any request. The tested `.explicitTeamMissing` branch only helps if an ID reaches the resolver ([QuickGameDay.swift](../../RollCall/QuickGameDay.swift#L21-L27), [QuickGameDayTests.swift](../../RollCallTests/QuickGameDayTests.swift#L84-L92)). Do not count that resolver test as proof of the saved-Shortcut case. Test a saved explicit-team Shortcut after deletion, with another remembered team present, and record whether iOS shows an error, asks for a new team, opens the app, or silently stops. Restoring a team should be tested separately because its identity may survive in Recently Deleted.

### I2 — IMPORTANT — Cold requests wait behind unrelated launch work and can briefly show another team

**Source-proven ordering; latency device-unproven.** `RootView.finishLaunchingTask()` awaits `AppModel.finishLaunchingIfNeeded()` before setting `hasResolvedInitialTab` and processing Quick Game Day ([RootView.swift](../../RollCall/RootView.swift#L815-L823)). That method waits for built-in asset setup, Apple Music capability refresh, readiness work, and generated-clip cleanup, and may prepare an incoming package ([AppModel.swift](../../RollCall/AppModel.swift#L873-L913)). The team state was already loaded synchronously during `AppModel` initialization, so routing is serialized behind work unrelated to choosing a team. For a populated previously selected team, `RootTab.sensibleInitialTab` starts on Game Day before an explicit request for a *different* team is processed ([RootView.swift](../../RollCall/RootView.swift#L8-L19), [RootView.swift](../../RollCall/RootView.swift#L496-L497)). A slow cold launch can therefore expose the previous team's live screen first, then switch. An early startup error still permits later routing once `finishLaunchingIfNeeded()` returns, but its alert can become a blocking presentation. Measure cold launch with differing selected, remembered, and explicit teams on a Release-installed device; the acceptance point is the correct visible team promptly, without a wrong-team intermediate live screen.

### I3 — IMPORTANT — The control's extension-to-app handoff is still a release evidence gap

**Device-unproven, not a demonstrated no-op.** The extension's first intent returns a second intent using `OpensIntent`; the second submits to an in-memory singleton ([QuickGameDayControlIntent.swift](../../RollCall/QuickGameDayControlIntent.swift#L41-L79)). If the second intent fails to execute in the app process, the extension's singleton cannot deliver a request to `RootView`; there is no persisted request or URL fallback in this path. Apple's control launch guidance uses a direct `OpenIntent` shared by both targets, while this implementation is a two-stage `AppIntent` result ([Apple control guidance](https://developer.apple.com/documentation/widgetkit/creating-controls-to-perform-actions-across-the-system)). The only control test calls the second `perform()` directly inside the app test host, bypassing the button, extension, first intent, process handoff, launch, and root rendering ([QuickGameDayTests.swift](../../RollCallTests/QuickGameDayTests.swift#L4-L22)). An earlier owner check reportedly verified the Control Center route on iOS 27 ([stabilization audit](../../SOL_ROLL_CALL_1.3_STABILIZATION_AUDIT.md#L135-L166)); that is useful positive evidence for that path, not proof of cold, locked, Action Button, or Release behavior. Run the matrix below before treating this integration as accepted.

### I4 — IMPORTANT — A successful intent result can precede, or never produce, visible navigation

**Source-proven sequencing.** Both app-side `perform()` methods return `.result()` immediately after `OpenGameDayRequestCenter.submit`, before `RootView` resolves or displays anything ([QuickGameDay.swift](../../RollCall/QuickGameDay.swift#L97-L114), [QuickGameDayControlIntent.swift](../../RollCall/QuickGameDayControlIntent.swift#L68-L80)). Root routing defers if an editor, import/export, error, lineup sheet, support screen, help sheet, or another listed presentation is active ([RootView.swift](../../RollCall/RootView.swift#L528-L548), [RootView.swift](../../RollCall/RootView.swift#L880-L903)). This protects active workflows, but Shortcuts or the control may appear to have completed while the old screen remains. The request can also be replaced by a second invocation before the blocking state clears because the center stores only one pending value ([QuickGameDayControlIntent.swift](../../RollCall/QuickGameDayControlIntent.swift#L41-L55)). The code retries when the blocking flag becomes false; it does not report deferral or replacement to the invoking surface. Test a backgrounded app with an editor or manual sheet still open, then foreground, dismiss, and invoke twice with different explicit teams. Establish the intended observable behavior and ensure no request is silently counted as reached without visible Game Day.

### I5 — IMPORTANT — Duplicate team names are indistinguishable in the explicit-team picker

**Source-proven data/UI ambiguity; actual Shortcuts presentation device-unproven.** Team creation and rename require a nonempty name but do not enforce uniqueness ([AppModel.swift](../../RollCall/AppModel.swift#L1247-L1261), [AppModel.swift](../../RollCall/AppModel.swift#L1323-L1334)). The entity has a stable UUID, but its `DisplayRepresentation` exposes only the team name as a title ([QuickGameDay.swift](../../RollCall/QuickGameDay.swift#L68-L77)). Two teams named alike can therefore appear with the same visible label in the Shortcuts team parameter picker; a coach can bind the wrong UUID and Quick Game Day will reliably open that wrong team. The resolver cannot detect this because both IDs are valid. Check the actual Shortcuts picker with two same-name teams before release and decide whether its system presentation supplies enough distinguishing context.

### I6 — IMPORTANT — Entity choices can lag live app state, and read failures masquerade as no teams

**Source-proven storage behavior; exact timing device-unproven.** The entity query reads only the last durable JSON snapshot and turns path/read/decode failures into `[]` ([QuickGameDay.swift](../../RollCall/QuickGameDay.swift#L80-L94)). App changes enqueue writes asynchronously ([AppModel.swift](../../RollCall/AppModel.swift#L4320-L4333)); the background flush helps after a scene transition but does not make a just-created, renamed, restored, or deleted team immediately visible to a foreground Shortcuts picker ([AppModel.swift](../../RollCall/AppModel.swift#L4351-L4367)). Stable IDs mean a rename should still route to the correct team when resolution succeeds, but the picker may show an old name. A transient read failure is indistinguishable from zero teams to Shortcuts, and a saved explicit ID may not resolve at all. This is specifically an App Intents exposure of the existing asynchronous persistence model. Test rapid create/rename/delete/restore followed by Shortcuts parameter editing and invocation; test state-file inaccessibility separately without treating an empty picker as proof that no teams exist.

## Scenario disposition

| Scenario | Source-level expectation | Remaining proof or risk |
| --- | --- | --- |
| Terminated app, remembered team | App target should initialize `AppModel`, receive app-side intent request, finish launch work, then select remembered ID and Game Day. | Cold timing, process handoff, and Release/device execution untested; I2/I3. |
| Backgrounded app | `openAppWhenRun` requests foreground; existing `RootView` observes singleton and routes after modal state permits. | Lock state, pending sheets, and SwiftUI observer timing need device checks; I4. |
| No teams | Resolver returns `.noTeams`; root chooses Players, but `shouldShowOnboarding` renders onboarding welcome/flow. | This is the normal zero-team entry, not an arbitrary team choice. It gives no Quick-specific explanation. |
| One team, no remembered team | Resolver returns `.noRememberedTeam`; root selects Teams. | Intentional policy even with exactly one team; do not mark this as wrong-team behavior. The cold initial tab may transiently be Game Day; I2. |
| Multiple teams, no remembered team | Teams screen; no first/selected-team guess. | Correct policy. Duplicate visible names still make explicit selection ambiguous; I5. |
| Renamed team | Saved UUID remains stable; query rebuilds name from state file. | Correct target after fresh persistence, possibly stale picker title; I6. |
| Deleted remembered team | Normal deletion clears `lastGameDayTeamID`; a stale ID in state falls back and is cleared on request. | No arbitrary replacement team; no user-facing fallback reason. |
| Deleted explicit team | Resolver would fall back if called with its ID. | App Entity resolution may stop before `perform()`; I1. |
| Repeated invocation | Each request has a new UUID; a pending request is overwritten. | Last wins while blocked; neither invocation receives navigation acknowledgment; I4. |
| Manual Setup Guide active | Resolver can select a valid team. | **Confirmed hidden destination and consumed request; B1.** |
| State-recovery screen active | Normal root event handlers are not mounted; pending singleton request may survive until recovery completes and normal root appears. | Recovery intentionally gates access to possibly unreadable user data. The URL handler is absent in recovery; device check if this route is relied on. |

## Playback, persistence, and existing behavior

The inspected Quick Game Day path submits a navigation request, selects/persists team state, and prewarms the next cue; it never calls `AppModel.play` or `CuePlaybackEngine.play` ([AppModel.swift](../../RollCall/AppModel.swift#L1211-L1233), [AppModel.swift](../../RollCall/AppModel.swift#L3867-L3876)). `prewarm` prepares a local `AVAudioPlayer` or preconnects catalog playback and does not start it ([Services.swift](../../RollCall/Services.swift#L1371-L1390)). **No new autoplay path was found in source.** Existing audio may already be playing when the app is backgrounded; navigation does not itself prove that audio stopped or restarted. Test with audio already active to distinguish continuation from autoplay.

**PRE-EXISTING:** App state recovery deliberately takes over the root view if the primary state cannot safely load. Quick Game Day cannot override that data-safety gate ([RootView.swift](../../RollCall/RootView.swift#L916-L921), [AppModel.swift](../../RollCall/AppModel.swift#L934-L935)). Likewise, asynchronous state persistence and foreground media preparation predate the intent integration; the new entity query and cold routing expose their timing. These are not grounds to bypass recovery or weaken persistence safeguards.

**DEFER:** The `rollcall://game-day` URL parser accepts a valid UUID and rejects an invalid one, with only a unit round-trip test ([QuickGameDayTests.swift](../../RollCallTests/QuickGameDayTests.swift#L94-L100)). It is not the active WidgetKit control transport. Multi-scene ordering is also low-priority on the current iPhone-only target: `WindowGroup` can instantiate more than one `RootView`, while the request center is process-global, so the first observing scene to consume a request may matter. Revisit only if a supported scene configuration makes that observable. Neither edge should be presented as a confirmed 1.3 failure.

## Release acceptance matrix

Run against an installed **Release** archive on representative physical iPhones, including the oldest supported iOS for Shortcuts (iOS 17) and supported control OS versions (iOS 18+). Log the visible screen/team and whether any audio starts, not just whether `perform()` returns or telemetry records a funnel event. Verify the extension is present in the installed app and the control appears in the system gallery. The Control Center check previously reported on iOS 27 should be repeated from a terminated app and while locked; also exercise Lock Screen and Action Button control placement where the device supports them. Action Button assignment through a Shortcut should be checked as the Shortcut path separately.

1. Create teams A and B, intentionally enter Game Day for A, browse B, then invoke an unparameterized Shortcut and each control from active, backgrounded, and terminated states. Expect A, no playback.
2. Run a saved explicit-B Shortcut in those states. Expect B, then relaunch and confirm B is now remembered. Rename B and repeat. Use same-name teams to inspect selection ambiguity.
3. Delete B after saving an explicit-B Shortcut; run it with A remembered. Record the system's pre-`perform()` behavior. Delete the remembered team separately; expect normal selection/home fallback, never an arbitrary remaining team.
4. Exercise zero teams, one team without remembered history, and multiple teams without remembered history. Confirm visible fallback and absence of unexpected audio.
5. Reopen the manual Setup Guide with a remembered team and invoke from each surface, warm and cold. B1 predicts a consumed request with onboarding still visible; this must be resolved or accepted explicitly before release.
6. Invoke while a player editor, lineup sheet, import/export prompt, support/help sheet, and error alert are open. Dismiss each, repeat rapidly with two explicit teams, and check final team, stale delayed navigation, and any invisible success.
7. Exercise a device after reboot before first unlock, then after unlock and while locked. Record whether App Intent parameter queries can read persisted teams and whether the control opens the app. Do not infer file-protection behavior from simulator results.
8. Measure cold invocation latency with a large existing team/media library and with a state-recovery prompt. Ensure the correct team is the first usable live screen, and that no Quick request causes playback.

The current unit tests cover resolver branches, URL parsing, and direct in-process execution of the destination control intent ([QuickGameDayTests.swift](../../RollCallTests/QuickGameDayTests.swift), [AppStatePersistenceTests.swift](../../RollCallTests/AppStatePersistenceTests.swift#L519-L583)). They do not cover system parameter rehydration, WidgetKit invocation, extension/app handoff, foreground transition, root presentation, locked state, or Release packaging. The specific acceptance criteria above close those gaps without adding intents or features.
