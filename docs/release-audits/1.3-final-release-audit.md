# Roll Call 1.3 final release-blocker audit

**Audit date:** 2026-09-23  
**Baseline:** last shipping 1.2.x tag, `v1.2.2-build80`  
**Candidate inspected:** `main` at `b9905bc` plus all uncommitted 1.3 changes present on the audit date (project file, app/model/photo/service/view files, tests, and documentation). The untracked `.claude/` directory was outside the application delta.  
**Scope:** investigation only. No application, test, project-setting, build-number, or existing documentation edits were made.

## Release judgment

| Classification | Count | Judgment |
|---|---:|---|
| BLOCKER | 0 confirmed | No new, reproducible crash, data-loss path, or broadly broken core workflow was established from the inspected source. This is **not** a device acceptance result. |

The single IMPORTANT finding is conditional on package contents, not every install. A normal small package round trip remains supported in the code. No code fix was attempted.

## IMPORTANT — valid self-exported and 1.2 packages can be rejected on import

**Affected workflow:** import audio or video → assign a local player song or Custom Clip → export a `.rollcall` team package → share/backup → preview or import that package on 1.3. It also affects previously exported 1.2 packages containing a sufficiently large local asset.

**Concrete evidence**

- [AudioAssetService.importMedia](../../RollCall/Services.swift#L454) accepts a non-video audio file and copies its original bytes through `storeCopiedAsset`; neither the current path nor its `v1.2.2-build80` counterpart caps file size. The player-facing file importer accepts `.audio` in [Player Editor](../../RollCall/RootView.swift#L8960).
- [PackageService.export](../../RollCall/Services.swift#L2307) stages and zips the team without checking the new import limits. [copyClipAssets](../../RollCall/Services.swift#L2853) copies the original local song source into the package unchanged. The shipping 1.2.2 exporter did the same.
- The new [ArchiveLimits](../../RollCall/Services.swift#L2275) are 256 MiB for the archive, 64 MiB for any uncompressed entry, 512 MiB total uncompressed, and a 1,000:1 maximum compression ratio. [validateArchiveBeforeExtraction](../../RollCall/Services.swift#L2746) runs before ZIP extraction and throws `AppError.invalidImport` when an entry crosses the 64 MiB limit. [previewDetails](../../RollCall/Services.swift#L2452) and import both use that extraction path, so the user cannot even reach the confirmation/repair UI.
- [testArchivePreflightRejectsOversizedEntry](../../RollCallTests/PackageServiceTests.swift#L647) deliberately proves the `64 MiB + 1 byte` rejection. [testAssetHeavyMultiPlayerPackageExportsAndRoundTrips](../../RollCallTests/PackageServiceTests.swift#L170) exercises only a package greater than 8 MiB; it does not cover the largest asset the app itself permits.
- In the shipping tag, the archive extraction path had no equivalent ZIP size preflight. This is a 1.3 compatibility regression, not a pre-existing import limit.

**Realistic consequence and reproduction:** A valid eight-minute, stereo, 44.1 kHz, 16-bit PCM WAV is about 80.7 MiB before its small WAV header. A coach can import it, select a short cue from it, and successfully export the team; the package still contains the full source. On 1.3, selecting that `.rollcall` file fails as an invalid import before preview. This can make a user-owned backup or transfer unusable even though Roll Call created it. A very compressible audio asset can also encounter the compression-ratio guard below the per-entry size cap; that case was not separately reproduced and is part of the same limit mismatch.

**Likely root cause:** The hostile-archive defense was added only to the reader. Its fixed limits were not checked against the existing media import and package export contracts or shipping 1.2 package sizes.

**Smallest safe fix:** Keep entry-path, symlink, duplicate, and bounded-extraction checks, but align accepted archive sizes with assets that 1.2 and 1.3 legitimately import and export. Use explicit, resource-bounded handling for larger valid packages, and add a round-trip fixture with a local audio entry above 64 MiB plus a representative shipping 1.2 package. Capping new exports alone would leave existing 1.2 backups unreadable.

**Confidence:** High from the size predicates and cross-file export/import path. I did not run an iPhone transfer or synthesize a large package in this investigation.

## PRE-EXISTING — interruption and media-service recovery remain unhandled

[AppModel.configurePlaybackAudioSession](../../RollCall/AppModel.swift#L4812) activates playback, while [CuePlaybackEngine.play](../../RollCall/Services.swift#L1287) interprets a tap on the currently active cue as stop. Current code observes route changes for readiness but has no `AVAudioSession.interruptionNotification` or media-services-reset handling. The same absence and tap-to-stop behavior are present in `v1.2.2-build80`; see [the existing issue record](../OPEN_ISSUES.md#p1-audio-session-interruptions-have-no-state-or-reactivation-recovery). A phone call or Siri interruption may leave a cue shown as active and require an extra tap to restart. This is a material live-use concern and deserves its own device decision, but source comparison does not support classifying it as a 1.3 regression. A prior attempted fix was rolled back after it broke announcement/song sequencing, so a speculative late replacement would carry real risk.

## DEFER / ruled-out candidates

1. **Draft photo orphan under a persistence-write interleaving.** [StatePersistenceWriter](../../RollCall/AppModel.swift#L4975) can return an unconfirmed result to an enqueue made while another write is active; an unreferenced draft-photo path staged with that enqueue may remain on disk until a later save. The asset reference check and delayed cleanup protect referenced media, and no path to deleting a user's current photo was established. This is storage cleanup, not a release blocker.
2. **Telemetry in developer/Internal builds.** [AppModel.makeDefaultTelemetryCoordinator](../../RollCall/AppModel.swift#L850) selects `NullTelemetryProvider` outside Release, despite the telemetry spec's developer Test Mode aspiration. Release/TestFlight uses the configured provider and pre-initialization analytics preference gate. This weakens non-Release telemetry observation but is not evidence that production users send forbidden values or lose a primary workflow. Do not expand 1.3 scope solely to change it.

The following earlier 1.3 stabilization issues were rechecked against the candidate and **not carried forward as open findings**: the app-icon Player Card crash now uses a separate drawable asset ([PlayerCards.swift](../../RollCall/PlayerCards.swift#L966)); profile framing has a single explicit presentation route ([RootView.swift](../../RollCall/RootView.swift#L9310)); recovery actions use one alert route ([RootView.swift](../../RollCall/RootView.swift#L7521)); unreadable primary state has a recovery decision path ([RootView.swift](../../RollCall/RootView.swift#L918), [AppModel.swift](../../RollCall/AppModel.swift#L940)); Apple Music metadata refresh preserves the current clip; and package ZIP entry/path checks are present. The removed compatibility-only built-in announcer profile was explicitly approved for 1.3 and did not protect a shipping 1.2 built-in announcer file; recorded Announcement Cues remain separate. These statements are source assessments, not new runtime acceptance claims.

## Cross-file workflow review

- **1.2 upgrade and persistence:** Compared schema-9 shipping state with the candidate's schema-11 [AppState codec](../../RollCall/Models.swift#L1380), launch/recovery handling, sequential migration, retained source-backed song choices, lineup/session normalization, and snapshot/asset references. The code preserves a pre-migration copy and does not silently replace an unreadable primary state on launch. Existing fixtures cover legacy decode and recovery logic, but the current candidate was not run on a device with a real 1.2 app container.
- **Team ownership:** Followed file import from [RootView](../../RollCall/RootView.swift#L929) through package preview, confirmation, service import, and [AppModel.performPackageImport](../../RollCall/AppModel.swift#L2689). The imported team gets a fresh team ID and an `Imported` name; team data is appended rather than overwriting a live team. Original and generated song assets, recorded announcements, and both profile/working-master photos are represented in export/import. The size mismatch above is the confirmed exception.
- **Photos and Player Cards:** Followed PhotosPicker selection, background decode/Vision preparation, request-ID cancellation, atomic master/profile writes, draft discard or commit, independent crop storage, Player Card rendering, and share presentation. The current code checks a request token before applying an asynchronous photo result and uses the saved legacy profile image when the working master is unavailable. No new confirmed photo deletion or stale-result overwrite was found. Device preview/framing/share behavior is still an acceptance gate.
- **Live playback and clip preparation:** Followed Game Day tap → current selected-team/player lookup → playback plan → announcer/song/fallback → structured start result, and clip generation queue cancellation/outcome matching. Current identity checks prevent applying a completed generated clip to a replaced assignment. No confirmed new 1.3 silence path was established; interruption behavior is recorded above as pre-existing.
- **Quick Game Day:** Followed Shortcuts entity/request creation, control intent handoff, the shared request center, cold-launch task, modal deferral, team resolution, and non-autoplay navigation. The iOS 18 extension is embedded in the app and the app target remains at iOS 17. Source review did not establish a failed request path, but process handoff and lock-state behavior require device proof.
- **Telemetry/privacy and Release:** Checked the typed event/property allowlist, preference gate before TelemetryDeck initialization, opt-out transition, privacy manifest, exact SDK pin, and Debug/Internal/Release compilation conditions. No confirmed personally identifying Roll Call event property or new production opt-out bypass was found. App Store Connect/privacy-policy alignment and actual Release/TestFlight signals cannot be proven by source inspection alone.

## Verification performed and remaining release gates

**Performed without modifying repository files:** `git diff`/tag comparison; targeted call-path and tests inspection; `swiftc -frontend -parse` of the changed/high-risk Swift sources (passed); `plutil -lint` for app/extension plists, privacy manifest, and project file (passed); `git diff --check` (passed). These checks establish syntax and the source relationships cited above, not runtime correctness.

**Not performed:** no build, XCTest execution, archive, install, or physical-device run. A read-only `xcodebuild -list -project RollCall.xcodeproj` attempt failed while resolving packages because this sandbox could not write SwiftPM diagnostic cache files; CoreSimulator service was also unavailable. The command did not validate a build. In addition, this investigation was authorized to make only the report file as a repository change, so it did not increment or alter the candidate's build number to run an app build.

Before a release decision, run the existing XCTest bundle and a Release-config archive/install, then use a real 1.2.x app container and physical iPhone for: upgrade with teams/songs/photos/backups, package transfer including a >64 MiB local source, imported profile/master photo recovery, repeated Player Card preview/framing/share, warm/cold Quick Game Day from Shortcuts and Control Center/Lock Screen, and Game Day playback/fallback through Music Library, Apple Music authorization/subscription states, Bluetooth/PA output, and interruptions. Verify the Release privacy manifest and App Store Connect/public privacy disclosures against the actual shipped binary. These are proof gaps rather than additional confirmed BLOCKER findings.
