# Roll Call 1.3 adversarial data-integrity audit

Date: 2026-09-23  
Scope: current `main` working tree, including its uncommitted 1.3 changes, compared with the shipping `v1.2.2-build80` tag. This is an investigation, not a code change or a release sign-off.

## Answer

Roll Call can keep a valid `state.json` while a referenced media file is missing or has different bytes. Its state write is atomic, but the state, backup manifests, and media files are not one transaction. The clearest *direct* user-data failures found are pre-existing: a new Announcement Cue can overwrite the audio a backup still names; restoring an earlier backup can leave the same team or player ID both active and in Recently Deleted, then restore it twice; and pruning the eleventh backup can delete a file still listed by the last durable state. A package with missing attachments also loses some saved media intent on import after its transient audit disappears.

The 1.3 persistence hardening materially improves malformed-state preservation, missing-primary detection, write ordering, and generated-clip startup safety. I found **no confirmed 1.3-specific direct-loss blocker**. One new coalesced-write path can strand unreferenced files; it is an important storage-integrity defect to address before 1.3, although it does not by itself erase a referenced asset. Physical device migration remains unverified by this code audit.

| Category | Finding | User-visible consequence |
| --- | --- | --- |
| **BLOCKER** | None established from a credible 1.3-specific path | This is not a claim that the release is verified. |
| **IMPORTANT BEFORE 1.3** | I1. Coalesced write can lose a staged cleanup notification | Orphaned photo/audio files survive; repeated failures increase storage pressure and can make later state writes fail. |
| **PRE-EXISTING / NOT WORSENED** | P1. Announcement Cue path reuse overwrites backup audio | A valid backup restores the wrong recording, or a failed replacement leaves it missing. |
| **PRE-EXISTING / NOT WORSENED** | P2. Backup restore retains conflicting Recently Deleted entries | Restoring the same item again creates duplicate IDs and ambiguous later edits/deletes. |
| **PRE-EXISTING / NOT WORSENED** | P3. Backup file pruning precedes durable record pruning | After interruption or failed state write, a listed backup is unreadable. |
| **PRE-EXISTING / NOT WORSENED** | P4. Missing package attachments lose photo/Announcement Cue intent | Imported model drops their paths; the missing-item audit is transient. |
| **PRE-EXISTING / NOT WORSENED** | P5. Explicit clip regeneration replaces a referenced file in place | Interruption can remove a local generated clip still named by state and backups. |
| **DEFER** | D1–D3 below | Lower exposure or no established direct-loss path. |

These labels separate provenance and release urgency. P1–P3 are serious even though they were present in 1.2.x; “pre-existing” does not mean harmless.

## Storage and ownership map

| Object | Authority and lifecycle | Failure boundary |
| --- | --- | --- |
| `Application Support/RollCall/state.json` | Authoritative `AppState`: teams, players, lineup/session fields, media references, Recently Deleted, and backup records. `AppModel.persist` snapshots in-memory state, then `StatePersistenceWriter` writes encoded JSON atomically (`RollCall/AppModel.swift:4320-4334`, `4370-4393`, `4963-5051`). | A successful `.atomic` replacement protects the JSON file itself, not the referenced files or an unacknowledged mutation. |
| `Assets/` | Imported local audio, photo masters/profiles, and recorded Announcement Cues. Photos use new UUID names before the draft is committed (`RollCall/RootView.swift:9273-9291`, `9383-9397`); most copied audio also uses UUID names (`RollCall/Services.swift:449-452`, `512-519`). | AppState stores relative paths. A path can remain syntactically valid while its bytes disappear or change. |
| `GeneratedClips/` | Derived song clips. Render output name is deterministic from clip ID and generation key (`RollCall/SongClipGenerationService.swift:182-204`). | Rebuildable for some local sources; an Apple Music source may not be locally readable on the next device. |
| `Snapshots/*.json` | Up to ten local state snapshots. They contain **references**, not copies of media. Normal backups remove Recently Deleted and nested snapshot lists (`RollCall/AppModel.swift:2953-2984`, `3563-3568`). | A snapshot can decode while its media has been replaced or removed. Its record and file are separately persisted. |
| `.rollcall` | Team package manifest at independent schema 9 plus copied attachments. Import creates new asset names and appends a new team ID, rather than replacing an existing team (`RollCall/Models.swift:1587-1596`, `RollCall/AppModel.swift:2689-2731`, `RollCall/Services.swift:2307-2336`, `2879-2927`). | The package can be incomplete; import's repair audit does not persist in AppState. |
| Preserved `state-unreadable-*` / `state-pre-migration-*` | Byte-for-byte recovery copy for unreadable or old primary state (`RollCall/AppModel.swift:4448-4508`, `4604-4625`). | These protect model bytes, not media bytes. |

`AppStateConsistencyValidator` checks active and Recently Deleted references at launch and logs missing/invalid paths; it does not repair or delete them (`RollCall/Models.swift:1487-1564`, `RollCall/AppModel.swift:802-815`). Assets removed by normal edits are staged and deleted only after a successful state-write result, with current active, Recently Deleted, and recorded-backup reference checks (`RollCall/AppModel.swift:3381-3407`, `3409-3487`, `4408-4441`). The generated-clip cleanup service additionally scans orphan snapshot files and fails closed on unreadable snapshots (`RollCall/GeneratedClipCleanupService.swift:26-50`, `120-153`).

## Findings

### I1 — Coalesced write can strand staged asset cleanup (**IMPORTANT BEFORE 1.3**)

**Path.** Replacing a photo or media reference stages its old path in `pendingAssetCleanupPaths`; each persistence request copies the set (`RollCall/AppModel.swift:1385-1400`, `3381-3395`, `4370-4393`). The 1.3 writer awaits a detached file write. While request A is writing, request B can enter the actor, replace `pending`, and return `.unconfirmed` immediately (`RollCall/AppModel.swift:4974-4980`, `4997-5021`). B's callback consequently does nothing with B's cleanup paths (`4438-4440`). When the writer finishes B, A's task receives the final `.written` result but applies **A's** cleanup set, not B's (`5022-5030`, `4323-4333`, `4413-4424`).

**Concrete sequence.** An earlier state write has started; the user replaces a player's photo, which stages the former master and profile and requests the new state. That request enqueues while the writer is suspended and returns `.unconfirmed`. The writer successfully writes the new state, yet neither callback consumes the former paths. If the app terminates before another `persist()` request captures them, those files remain permanently unreferenced. The same mechanism applies to local audio and generated clips. There is no proof here that this interleaving deletes a still-referenced asset; the observed integrity failure is an orphan leak. Unlike the shipping 1.2.2 writer, the current writer suspends within `writePending` (`v1.2.2-build80:RollCall/AppModel.swift:4151-4209`).

**Why it matters.** Photos are durable, potentially large files. Accumulated orphan files can exhaust storage; a later `state.json` write then fails and the user can lose subsequent in-memory edits. A normal subsequent save or scene flush may clear the staged paths, so the exposure requires termination before that later successful request. Verify with a controlled writer interleaving and file inventory, not a sleep-based test.

### P1 — A cleared Announcement Cue can overwrite backup audio (**PRE-EXISTING / NOT WORSENED**)

**Path.** The first recording for a player uses `custom-intro-{playerID}.caf`; a replacement uses a fresh UUID only if the *current* player still has a path (`RollCall/AppModel.swift:1889-1909`, `RollCall/Services.swift:490-505`). Clearing the cue sets that current path to nil (`RollCall/AppModel.swift:1954-1961`). Backups retain the original path and asset-reference checks protect it from ordinary deletion (`RollCall/AppModel.swift:3429-3487`). On the next recording, the nil path selects the original deterministic name, `storeCustomAnnouncerRecording` removes the existing file, then writes the new bytes.

**Concrete sequence and impact.** Record cue A → make a backup → clear the cue → record cue B for the same player → restore the backup. The backup's valid JSON still names A's path, but that path now contains B. If removal succeeds and the new write fails or the process ends between them, the backup instead names no file. Neither the backup-reference check nor `.atomic` writing of the new data prevents this in-place replacement. The same selection/removal code exists at `v1.2.2-build80:RollCall/AppModel.swift:1329-1337` and `v1.2.2-build80:RollCall/Services.swift:508-523`.

**Acceptance check.** Compare the backup's referenced asset bytes before and after clear/re-record, then restore. A state-only round trip cannot detect this.

### P2 — Backup restore and Recently Deleted can create duplicate IDs (**PRE-EXISTING / NOT WORSENED**)

**Path.** Normal backup snapshots exclude Recently Deleted; restore loads old `teams` but deliberately copies the *current* `recentlyDeleted` into the restored state (`RollCall/AppModel.swift:3012-3027`, `3563-3568`). The Recently Deleted restore checks the original team exists, then appends the saved team or inserts the saved player without checking whether its ID is already active (`RollCall/AppModel.swift:3039-3058`, `3061-3101`, `3683-3700`, `3703-3744`). `AppState` decode does not enforce uniqueness across those collections (`RollCall/Models.swift:1286-1300`).

**Concrete sequence and impact.** Back up team T with player P → delete P (or T) → restore the earlier backup. P (or T) is active again, while the deleted record still exists. Tapping Restore in Recently Deleted inserts the same ID again. Lookup and mutation methods commonly use `firstIndex(where: id == ...)` (`RollCall/AppModel.swift:1348-1359`, `1385-1395`, `1671-1698`), so one duplicate can shadow the other; later edits/deletes may affect the wrong copy or appear to revert. The same restore merge existed in shipping 1.2.2 (`v1.2.2-build80:RollCall/AppModel.swift:2372-2394`). The existing test deliberately verifies retention of Recently Deleted across restore, but uses a different restored team and therefore does not cover ID collision (`RollCallTests/BackupRestoreTests.swift:141-193`).

**Acceptance check.** Restore a pre-deletion snapshot for both a deleted team and a deleted player, then invoke item-level Restore and inspect unique IDs, selection, lineup, and subsequent edits.

### P3 — Backup pruning happens before its record change is durable (**PRE-EXISTING / NOT WORSENED**)

**Path.** On creation of an eleventh snapshot, `insertBackupRecord` drops the oldest record and starts detached deletion of its file immediately; only afterward does the caller issue an asynchronous `persist()` for the new record list (`RollCall/AppModel.swift:2929-2944`, `2979-2994`). The old primary state may still list that oldest snapshot. The same order appears at `v1.2.2-build80:RollCall/AppModel.swift:2339-2354`.

**Concrete sequence and impact.** Ten backups exist → create one more → file pruning runs → state write fails or the app terminates before it lands. On next launch, valid `state.json` still lists the pruned backup, but its file is gone. Restore from that row fails; asset cleanup also sees an unreadable recorded snapshot and conservatively retains assets (`RollCall/AppModel.swift:3455-3465`). The immediate loss is a rollback point, not the live team model. It also demonstrates that a successful atomic state write cannot make the backup record/file pair transactional.

**Acceptance check.** Interrupt or fail the state write after the eleventh snapshot file has been removed, then relaunch and attempt the oldest listed restore.

### P4 — Missing package attachments lose persistent repair information (**PRE-EXISTING / NOT WORSENED**)

**Path.** Export quietly omits an attachment when its referenced source file is absent (`RollCall/Services.swift:2834-2876`). Preview/import audits missing photo, photo source, and Announcement Cue files (`RollCall/Services.swift:2496-2522`), but import replaces their model paths with `nil` when the attachment is missing (`RollCall/Services.swift:2894-2925`, `3059-3079`). The audit is held in `completedPackageImportAudit`, a non-persisted `AppModel` property (`RollCall/AppModel.swift:644-650`, `2725-2731`). Shipping 1.2.2 already imported missing photo and Announcement Cue attachments this way (`v1.2.2-build80:RollCall/Services.swift:2521-2555`).

**Concrete sequence and impact.** A team's Announcement Cue or photo file is missing on the source device, but its AppState still records the choice. Export a `.rollcall` package, import it, and relaunch. The imported player no longer records that photo or Announcement Cue path; the one-time repair audit is gone. If an old file later becomes available, the imported model cannot associate it automatically. Local song audio is handled more conservatively: it retains the source's display metadata and a sentinel missing path (`RollCall/Services.swift:2939-2955`). The incomplete package is still useful, and no existing team is overwritten, but it is not a lossless recovery of saved media intent.

**Acceptance check.** Export/import a team with a deliberately missing photo and Announcement Cue, then relaunch and inspect persistent repair cues and the model, not only the immediate import audit.

### P5 — Explicit generated-clip replacement is not failure-atomic (**PRE-EXISTING / NOT WORSENED**)

**Path.** Normal automatic preparation skips an existing ready generated file, but an explicit Try Now bypasses that skip (`RollCall/AppModel.swift:4005-4018`). Rendering uses a deterministic `clip.id`/generation-key path and removes any existing destination before moving the newly rendered temporary file (`RollCall/SongClipGenerationService.swift:182-204`). An active request canceled after generation may also remove its returned path (`RollCall/SongClipGenerationQueue.swift:165-170`).

**Concrete sequence and impact.** A ready generated clip is still referenced by live state or a snapshot; the user requests explicit regeneration of the same clip. If removal succeeds but the move fails or the process terminates, the valid state and backup still name the now-missing file. The original local source may permit regeneration, but an Apple Music-linked source may not be readable offline, so the fallback can be materially worse. This render path was present in 1.2.2; the current 1.3 startup cleanup being audit-only does not address in-place regeneration.

**Acceptance check.** Force a failure after destination removal during explicit regeneration; verify the previously playable file survives and both live state and a snapshot still resolve it.

## Upgrade, termination, and recovery assessment

- **Shipping 1.2.x migration.** The shipping 1.2.2 AppState schema is 9; current AppState is 11, with ordered steps through 10 and 11 (`RollCall/Models.swift:1216-1228`, `1362-1466`). Team-package schema remains 9 independently (`RollCall/Models.swift:1595-1607`). The current player decoder still migrates a legacy `cue` into a private song assignment, and team decoding resolves legacy shared assignments (`RollCall/Models.swift:384-395`, `709-727`). The removed built-in announcer compatibility fields are explicitly documented as never shipped (`docs/DECISIONS.md:7`); I did not count their removal as a shipping-data regression. The current tests cover a synthetic schema-10 round trip and malformed schema cases (`RollCallTests/AppStatePersistenceTests.swift:112-190`), but this audit found no literal shipping schema-9 fixture or real-device upgrade proof.
- **Interrupted and failed state writes.** Every mutation calls `persist()` asynchronously; the writer coalesces by increasing sequence and uses `.atomic` JSON replacement (`RollCall/AppModel.swift:4320-4334`, `4963-5051`). Scene transition requests a background-task flush (`RollCall/RootView.swift:789-795`, `RollCall/AppModel.swift:4351-4367`). A force termination before the first write, or a full-disk/write failure followed by termination, still loses the latest in-memory edit; failure is surfaced through `lastError` but is not retried until another persistence request. This exposure is inherited from 1.2.x. For package import and CSV apply, the pre-operation snapshot file is created before mutation, but its record and the imported result are also persisted asynchronously (`RollCall/AppModel.swift:2696-2731`, `2796-2804`, `2939-2944`). A just-imported team can therefore disappear after an immediate termination while its copied assets remain orphaned; the original package may need to be re-imported.
- **Unreadable or missing primary.** Current launch preserves unreadable/future primary bytes and blocks ordinary lifecycle writes; a missing primary with meaningful assets/snapshots enters recovery instead of silently writing an empty state (`RollCall/AppModel.swift:4448-4508`). Recovery writes and reloads a replacement before leaving the recovery screen (`RollCall/AppModel.swift:1017-1108`). Startup generated-clip cleanup only audits, and after missing-primary Start Fresh it preserves residual files (`RollCall/AppModel.swift:899-907`, `1099-1103`, `3149-3154`). These are meaningful safeguards, not evidence that a state snapshot contains its media.
- **Photo lifecycle.** New master/profile photo files are written under distinct UUID names before their paths enter the draft; failure of either write removes both new files (`RollCall/RootView.swift:9273-9291`). Save commits draft paths to the model; discard stages only uncommitted paths (`RollCall/RootView.swift:9416-9420`, `9458-9479`). Reframing writes a new profile name (`9383-9397`). This avoids normal in-place photo overwrite. Termination between asset write and model commit can leave an orphan; termination after model commit but before state write can revert to the old photo while the new files survive. Backups protect *recorded* prior paths, subject to P3.
- **Deletion and Recently Deleted.** Team, player, and Custom Clip deletion first move model payloads to the 60-day Recently Deleted list, retaining their asset references (`RollCall/AppModel.swift:1348-1367`, `1633-1662`, `1671-1698`, `RollCall/Models.swift:1004-1013`). Expiry/permanent deletion stages cleanup, and current references are rechecked after a successful state write (`RollCall/AppModel.swift:3105-3109`, `3555-3571`, `4408-4424`). P2 is the collision exception after whole-app backup restore. Missing photo source on item restore is explicitly degraded to profile-only after a partial-restore choice (`RollCall/AppModel.swift:3609-3644`, `3747-3755`).
- **Package replacement/import.** Normal `.rollcall` import appends a new UUID team with “ Imported” in its name; it does not replace an existing team (`RollCall/AppModel.swift:2702-2731`). Imported attachments receive fresh UUID paths and a thrown import removes already recorded new paths (`RollCall/Services.swift:2384-2406`, `2879-3079`). Export creates a temporary archive from a staged manifest and asset copies (`RollCall/Services.swift:2307-2336`); the share lifecycle cleans only that exact temporary file (`RollCall/AppModel.swift:2643-2647`, `RollCall/Services.swift:2340-2352`). I found no credible normal path here that overwrites another team's assets. P4 concerns incomplete packages, not team replacement.

## Deferred observations and verification limits

1. **D1: Semantically incomplete but valid JSON.** `AppState.init(from:)` defaults a missing `teams` key to `[]` (`RollCall/Models.swift:1286-1300`). A syntactically valid, damaged `state.json` containing only a schema version can therefore load as an empty app and be rewritten, bypassing unreadable-state recovery. Normal `.atomic` writes do not produce that shape, and I found no in-app path that does, so this is a hardening gap rather than a demonstrated 1.3 loss path. Test with actual partial device/container restore evidence before raising severity.
2. **D2: Manual generated-clip cleanup uses a stale snapshot window.** `cleanGeneratedClipsNow` captures an activity count and serializes state before a detached cleanup scan/delete (`RollCall/AppModel.swift:3141-3184`, `RollCall/GeneratedClipCleanupService.swift:79-95`). New preparation or assignment during that interval is not reflected in the captured state. This is an inherited manual action; startup 1.3 cleanup is audit-only. I did not establish a likely UI sequence that removes the sole copy of user-owned audio, so this remains a targeted concurrency test candidate.
3. **D3: Malformed schema upper-bound conversion.** `AppStatePersistenceCodec.schemaVersion(in:)` compares a `Double` against `Double(Int.max)` and then converts to `Int` (`RollCall/Models.swift:1363-1381`). Because those doubles round to the same value at the upper boundary, a deliberately malformed `9223372036854775808` schema number passes the comparison and can trap during conversion instead of entering recovery. This is a deterministic malformed-input defect, but the app has no normal route that writes such a version. It does not justify claiming ordinary user-data loss without a plausible source for those bytes.

**Verification performed:** targeted static tracing of model/asset call sites, current tests, current product decisions, and line-by-line comparison with the `v1.2.2-build80` tag; a bounded independent adversarial review challenged the highest-risk conclusions. No production code, tests, settings, or build numbers were changed. No Xcode build or test run was performed: this investigation was read-only with respect to app code, and an actual app build would require a build-number edit under the repository working agreement. No physical iPhone migration, full-disk, power-loss, or forced-termination experiment was performed. These findings identify executable code paths and their conditions; timing-dependent outcomes still need fault-injection or device validation before claiming observed field frequency.
