## 1. Current telemetry inventory

### Boundary and interpretation

The source declares **101** Roll Call events. Feature code reaches the SDK only through `RollCallTelemetryCoordinator` and `TelemetryDeckProvider.send`; the provider calls `TelemetryDeck.signal` with a fixed enum name and validator-approved values ([Telemetry.swift:8](../../RollCall/Telemetry.swift#L8), [Telemetry.swift:163](../../RollCall/Telemetry.swift#L163), [Telemetry.swift:394](../../RollCall/Telemetry.swift#L394)). Every ordinary signal receives `telemetrySchemaVersion=1`. The event-specific payloads below are **additional** properties. `appVersion` and `buildNumber` are declared property names but are never allowed for an event or attached by the Roll Call layer. The SDK may add its own version/run/device metadata. There is no arbitrary property or raw-error pass-through.

The `ordinaryRecordingGate` and available-store check guard every ordinary `record` call. Once/milestone methods also consume local history while opted out, so re-enabling does not backfill it. The exceptions are the explicit `analytics.preferenceChanged` off/on transition and, while the preference remains enabled, the narrow `telemetryState.persistenceFailed` signal after telemetry-store failure. Pending live signals carry a preference generation and are discarded across opt-out ([Telemetry.swift:1343](../../RollCall/Telemetry.swift#L1343), [Telemetry.swift:1418](../../RollCall/Telemetry.swift#L1418)). SDK-queued signals can still arrive after opt-out, as disclosed. `NullTelemetryProvider` is selected outside Release even though the context computes Test Mode; hence **can emit** below means the code can construct/send a signal in a configured Release/TestFlight build, subject to gate, storage, and SDK delivery. Debug/Internal calls do not reach the service ([AppModel.swift:850](../../RollCall/AppModel.swift#L850)).

In the table, **I** = once per local telemetry installation; **T** = once per team; **G** = once per probable live checkpoint or per listed combination within it; **R** = raw/repeatable; **B** = pre-existing-state enrollment baseline can also emit it with `observationOrigin=enrollmentBaseline` (otherwise observed occurrences use `observedAction` where applicable). “Success” means the stated app-side boundary, never remote ingestion. All listed events are subject to the gate above unless marked **narrow**. Rows marked **declared only** have no production call site and cannot currently emit. Usefulness is assessed for current 1.3, not historical design intent.

### Cross-event timing and opt-out notes

One-time events are deduplicated by local keys; raw UI and reliability events can recur. Probable-game feature events are buffered until the checkpoint qualifies. Several thresholds can emit together after one action. The local checkpoint contains team/player UUIDs and exact dates **only on device**, not in the transmitted properties; this is intentional for deduplication and the probable-game heuristic. Product adoption events generally follow canonical in-memory mutation and persistence scheduling, **not** asynchronous AppState disk acknowledgement, per the approved catalog's commit boundary ([spec:54](../telemetry/ROLL_CALL_TELEMETRY_SPEC.md#L54)). They can therefore overstate retained state if a later write fails; `state.persistenceFailed` separately reports that condition. Provider delivery is batched and not acknowledged by these call sites.

## 9. Proposed revised event catalog outline

This is an **outline for a later implementation decision**, not an edit to the active catalog. Preserve event names/historical meaning unless a schema version and dashboard migration are planned.

1. **Envelope and privacy:** `telemetrySchemaVersion`; verified SDK app/build/environment fields or explicit fixed Roll Call app/build fields; common opt-out rule and narrow exceptions; no user content, file identifiers, raw errors, or stable Roll Call IDs.
2. **Activation:** onboarding start/completion/import handoff; roster/team and first-personalization thresholds; explicit distinction between baseline-observed and new actions.
3. **1.3 visual workflow:** Card preview opened → render success/failure → share sheet initiated → **completed system activity with `design`**; photo first add/replacement, coarse detection and committed framing adjustments only if their analysis remains useful.
4. **Live use:** confirmed first playback, playback depth, probable game, mode/source/accent/settings at qualification, per-game lineup/Clips/announcement feature flags. Define “started” versus “completed” clearly.
5. **Reliability:** raw complete playback failures; deduplicated affected probable-game failure and fallback combinations; typed permission failures; package preview/commit failure phases; app-state incident detection, telemetry-store recovery/persistence, and latest AppState persistence failure. 6. **Ownership/recovery:** completed package share activity, import outcome including truthful device review, manual backup and restore, Recently Deleted restore with optional coarse full/partial item category, and CSV import.

8. **Retirement list:** unreachable `quickGameDay.failed` until a real emitter exists; unsupported Card failure reasons; misleading `live.entered` dashboard label; potential low-value detection/raw-render volume. Document retained historical names and effective schema/build boundaries if changed.
