# Roll Call 1.3 — Player Photo and Player Card adversarial audit

**Date:** 2026-09-23

**Scope:** Current working-tree implementation of Player Editor, photo preparation and framing, persistence and asset ownership, the three shipping Player Card renderers, preview, and system sharing. Investigation only; no production code, tests, settings, or build numbers were changed. The working tree already contained unrelated edits when this audit began.

## Disposition

One **BLOCKER** can persist a profile image from a different source than the saved working master. Three **IMPORTANT** issues can produce stale card output, lose the selected per-player design, or frame a bystander in a multiple-person photo. A pre-existing identity-clipping limit and three lower-confidence lifecycle gaps are recorded separately. These are code-path findings, not claims of device reproduction. The existing unit tests were inspected but not run; representative device interaction, Photos picker timing, Save to Photos, and Share Sheet behavior remain unverified.

Severity here means: **BLOCKER** should be resolved before 1.3 release because saved player identity can become inconsistent; **IMPORTANT** is a meaningful 1.3 correctness or regression risk; **PRE-EXISTING** predates the current card-design work; **DEFER** has a concrete code gap but lacks an ordinary-user trigger or confirmed visible failure.

## Lifecycle traced

1. `PlayerEditorSheet` uses `PhotosPicker` with `photoItem` and resets the binding to `nil` before starting each import (`RollCall/RootView.swift:8675-8678,8911-8915`). A request UUID and stored task supersede prior imports; the form, Close, and Save are disabled during preparation (`RootView.swift:8892-8909,9230-9271`). This addresses stale `PhotosPickerItem` identity and ordinary rapid replacement.
2. `PlayerPhotoPreparationService` decodes an orientation-normalized, at-most-3000-pixel working master, performs local Vision face/person/upper-body detection, then emits a master JPEG, 640-square profile JPEG, and separate normalized profile/card crops (`RollCall/PlayerPhotos.swift:109-203`). Failed Vision detection falls back to geometry; the original Photos asset is not kept as an app-owned source.
3. The editor writes master and profile under fresh UUID filenames with atomic writes and rollback on write failure. It holds new paths as draft assets until Save, removes replaced draft paths, and discards uncommitted paths on Close/disappearance (`RootView.swift:9273-9298,9416-9420,9458-9480`). `AppModel` merges the four photo fields into the saved player and removes old assets only when no team, recovery item, or backup snapshot references them (`RollCall/AppModel.swift:1424-1445,3381-3406,3409-3426,3483-3486`).
4. With a readable master, manual Profile framing writes a new compact JPEG and profile crop without changing the card crop; manual Card framing changes only `playerCardPhotoCrop`. If a configured master is unreadable, falling back to the compact photo also clears master-dependent crop/source fields (`RootView.swift:9317-9321,9374-9404`; `RollCall/PlayerCards.swift:1257-1263,1303-1325,1353-1361`). Legacy cropped-only players remain supported. Package export/import includes both photo files and the crop fields, and drops master-dependent crops if the master is absent on import (`RollCall/Services.swift:2841-2849,2894-2910`).
5. Preview loads the master when readable, otherwise the compact photo; it renders Spotlight, Impact, and Broadcast from the same `PlayerCardContent`, photo, and crop at 1200 × 1500. The chosen image is passed as a `UIImage` snapshot to `UIActivityViewController` for Share or Save (`PlayerCards.swift:866-897,1196-1202,1297-1351,1442-1449`). No card file or persistent rendered-card cache is created. Compact thumbnails use immutable-path `NSCache` keys; normal replacement changes filenames, so a same-key stale thumbnail was not found (`RootView.swift:10011-10102`).

## Findings

### RESOLVED — A pending Profile framing request cannot apply the previous photo after replacement

**Original evidence.** Before this fix, `presentPhotoFraming` captured an image for detached Vision work and checked only `photoFramingRequestID` on completion. `beginPhotoImport` advanced a separate request ID without invalidating framing, and Apply derived the source path from the current draft instead of the captured image's source.

**Protection.** `beginPhotoImport` now invalidates the framing request and dismisses any framing presentation. Each framing token records whether its source is the working master or a legacy profile, plus its exact path. Both presentation and Apply require the token to remain active and match the draft's current source. Apply uses that validated captured path before creating or writing a derived profile. Detached Vision work may finish, but its result cannot present or mutate the draft.

**Regression coverage.** `PlayerPhotoTests.testStaleProfileFramingCannotApplyOrPersistAfterPhotoReplacement` deterministically replaces A with B before completing A's request and verifies that profile, master, and both crops for B survive serialization. Separate tests cover normal profile adjustment, Player Card crop independence, and legacy-profile source matching.

**Verification.** The Roll Call simulator build and focused `PlayerPhotoTests` plus the Player Editor draft-state test passed on iPhone 17 Pro (iOS 27.0). Physical-device interaction remains an owner verification step.

### RESOLVED — A cancelled card render can publish an obsolete crop, including after the newer render

**Protection.** Each preview render has a unique request UUID and an immutable identity containing all `PlayerCardContent`, both photo paths, and the Player Card crop. The three card images, framing image/options, and working-master flag publish together only after the active request and current identity match. The detached renderer receives cancellation and checks it between designs; identity is checked after card rendering, after Vision framing analysis, and again at publication. Stale successes and failures are ignored, including their callbacks. The framing editor is tied to the accepted request and revalidates it before Apply. Share reads only the selected design from the accepted current bundle. The design selector remains an app-wide last-used preference and does not trigger a render.

**Regression coverage.** `PlayerCardTests.testStalePlayerCardRenderCannotReplaceOrApplyAfterPhotoReplacement` publishes B before stale A and verifies A cannot publish, change B's draft photo/crops, replace B's framing data, or change the Share image. `testPlayerCardRenderRequestUUIDRejectsEarlierAAfterBThenA` covers A→B→A. `testCurrentPlayerCardRenderPublishesEveryShippingDesignAndFramingForShare` verifies an ordinary accepted render contains all shipping designs and usable framing.

**Verification.** The Roll Call iOS Simulator build and focused `PlayerCardTests` plus `PlayerPhotoTests` passed on iPhone 17 Pro (iOS 27.0): 39 tests, zero failures. Physical-device interaction remains an owner verification step.

### IMPORTANT — The design picker persists only a global last-used design, not this player's design

**Evidence.** `Player` has `playerCardDesignID`, it is encoded, included in draft-change detection, and merged on editor Save (`RollCall/Models.swift:277-314,378-408,448-465`; `AppModel.swift:1430-1438`). The preview is initialized from `appModel.lastPlayerCardDesign`, and changing its selection updates only `AppSettings.lastPlayerCardDesignID` (`RootView.swift:9002-9010`; `PlayerCards.swift:1127-1157,1230-1234,1281-1295`; `AppModel.swift:2390-2395`). No preview path assigns the selected design to `player.playerCardDesign`. This conflicts with the additive per-player design persistence described in `docs/DECISIONS.md:13`; serialization tests verify the field, but not the UI transaction (`RollCallTests/PlayerCardTests.swift:88-106`).

**Failure sequence.** Choose Broadcast for player A, then Impact for B. Reopen A: the picker starts at Impact, while A's stored `playerCardDesignID` remains its prior value. Saving A does not correct it. The choice follows the last card viewed, so repeated use does not retain a player's selected composition.

**Smallest safe fix.** Bind deliberate design changes into the Player Editor draft and initialize from the player's supported saved design. Define the app-level last-used value only as a fallback where intended. Preserve an unknown future raw ID when a user merely previews and closes without deliberately changing the design. Add a UI/state test covering two players, Save, Cancel, and reopen.

### IMPORTANT — Automatic Card framing can combine one person's face with another person's body

**Evidence.** Vision's primary face and largest/central person rectangle are selected independently (`PlayerPhotos.swift:262-270,339-372`). If no matching upper-body rectangle exists, `upperBodyAnchor` uses the independently chosen full person; the automatic card anchor is `upperBodyAnchor.union(faceAnchor)` (`PlayerPhotos.swift:288-303`). `analyze` recognizes a face/person mismatch as `.multiplePeople` but uses that result only as metadata, not to alter the card crop (`PlayerPhotos.swift:226-253`). The profile crop follows the primary face (`PlayerPhotos.swift:273-286`). Existing multiple-person tests cover a matching central subject and the supplied catcher image with a matching upper-body observation, not the mismatched-body case (`RollCallTests/PlayerPhotoTests.swift:147-193`).

**Failure sequence.** Vision detects the intended player's face but detects only, or scores more highly, a bystander's full body; no upper-body box matches the face. The profile crop can show the intended player while the automatic card crop expands toward the bystander, potentially favoring that person. The `.multiplePeople` result does not prompt correction.

**Smallest safe fix.** Anchor automatic card framing to a body spatially associated with the selected face. When none matches, derive the automatic card crop from the face anchor. Retain the multiple-person detection result and add a synthetic mismatch regression fixture.

### PRE-EXISTING — Spotlight can clip a long player name in the exported identity

**Evidence.** The existing Spotlight renderer passes the name into a fixed-width 980-point box (`PlayerCards.swift:924,992-1004`). Its font fitter stops at a 40-point minimum even when the string still exceeds that width, and the surname is drawn with `.byClipping` (`PlayerCards.swift:995-1017`). Player Editor's name field has no length bound (`RootView.swift:8659-8665`). Thus a sufficiently long valid name can be cut off in the final card, not just its preview. This rendering path predates the three-design selector. Impact and Broadcast also use bounded minimum-font/clipping paths (`PlayerCards.swift:537-603,428-454`), but this audit did not establish a realistic-name failure in those new designs. The current card tests check successful encoding and dimensions, not that identity text remains visible (`RollCallTests/PlayerCardTests.swift:31-70,239-255`).

**Smallest safe fix.** Establish representative upper-bound names and numbers, inspect final exported pixels for each shipping design, then allow a smaller font, wrapping, or a visibly intentional truncation rule where needed. Do not infer legibility from a non-nil PNG.

### DEFER — The crop editor does not show Impact and Broadcast's exact visible photo area

The card crop and editor use Spotlight's 1092:900 photo ratio (`PlayerPhotos.swift:206-208`; `PlayerCards.swift:1251-1254`). Impact's photo viewport is 992:936 and Broadcast's is 996:1020 (`PlayerCards.swift:694-696,761-762`). Their scale-to-fill transform centers the same stored crop in a narrower aspect (`PlayerCards.swift:248-269,381-385`), trimming about 6% and 10% respectively from each side of what the editor showed. An edge-framed face may therefore be absent from an Impact or Broadcast card even after a seemingly correct manual adjustment. All final designs are previewed before sharing, and no representative subject-loss case was verified, so this remains a conditional risk. Check edge-positioned subjects in final exports for each design; if reproduced, make the editor reflect the selected design's actual photo viewport or show its safe visible bounds without changing stored photo data casually.

### DEFER — Team/song changes can leave an already-open preview stale

`renderIdentity` contains the player's name, number, photo paths, and card crop, but omits player/team IDs, team name/accent, and song/artist content (`PlayerCards.swift:1271-1279`). Rendering snapshots `PlayerCardContent(player:team:)` once (`PlayerCards.swift:1303-1308`). If the bound team's data or song metadata changes while preview remains open without one of the included player fields changing, `.task(id:)` does not rerender and sharing uses the old image. The ordinary modal UI makes this uncommon; background metadata refresh or an external model update are plausible triggers. Include the full immutable render inputs in the generation key or compare them before Share. This is distinct from the confirmed crop race above.

### DEFER — A failed draft commit after external deletion can orphan newly written photo files

`commitPlayerEditorDraft` silently returns if the selected team's player ID no longer exists (`AppModel.swift:1424-1427`), while `saveAndDismiss` unconditionally marks the draft committed and clears its owned-path set (`RootView.swift:9458-9474`). If a player/team is removed externally while a photo draft is open, Save can leave newly written UUID assets unreferenced and unqueued for cleanup. Root's ordinary sheet routing and import-time disabled controls make this hard to trigger through the normal UI (`RootView.swift:634-636,1164-1165,8892-8909`). Return a commit result and retain/discard draft ownership on failure; anchor an editor session to team ID as well as player ID if external team changes become supported.

## Checks and release validation gaps

- **Confirmed by code trace:** stale picker selection is reset; import completion is request-gated; new master/profile files have unique names and atomic writes; profile and card crops persist independently; ordinary photo replacement changes thumbnail cache keys; all three shipping card designs render from the same selected source/crop; Share/Save captures one selected `UIImage` without an app-owned export file.
- **Automated tests run after the fixes:** the focused PlayerCardTests and PlayerPhotoTests suites passed (39 total). They cover photo preparation/geometry, stale Profile framing after replacement, stale Player Card render completion, A→B→A request identity, all shipping card designs, and usable framing/share output. Per-player design selection and visible long-name bounds remain outside this fix.
- **Device work still needed:** verify replacing a photo during pending Profile framing, quickly applying successive Player Card crops, and sharing/saving the selected card after the final crop; inspect realistic multi-person photos and long names/numbers in Spotlight, Impact, and Broadcast; switch designs repeatedly; cancel and reopen Share Sheet; delete/restore a player or team after photo work; verify VoiceOver framing and the supported iPhone-size matrix. No physical-device result is claimed by this report.
