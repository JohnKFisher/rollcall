# Where We Stand

Use this file as a concise project status snapshot for the current version, what works, known limitations, and next priorities.

## Roll Call

Current version: `1.2` (build `66`)

Status:
- Cue revamp Phase 2 now includes a readable-local generation and reliability engine. Roll Call can render selected windows with a tiny fade-in and baked fade-out to app-owned `.m4a` files, process one preparation job at a time, persist pending/success/failure state, retry retryable failures at bounded delays, reject stale results, and preserve an older working generated clip when regeneration fails.
- Preparation is triggered after song assignment, app launch/foreground, Player Editor and Readiness entry, Music authorization changes, and package import repair. It pauses during Game Day, Clips, and Low Power Mode; an explicit `Try Now` may bypass Low Power Mode but not live-use pauses.
- Active Apple Music download requests were not implemented because the public iOS SDK does not provide an API to request or control an offline Music download. Roll Call does not use `addItem(withProductID:)` as a substitute. It only observes existing Music Library/device state and uses `MPMediaItem.assetURL` when iOS legitimately exposes a readable file.
- Cue revamp Phase 1 now has the new durable song model foundation: player songs persist as `SongAssignment`/`SongClip` data, teams can carry a future team-scoped clip library, legacy `Player.cue` state and older `.rollcall` packages migrate to private player assignments when decoded, and the existing `Cue` playback/editor surface remains operational through a compatibility accessor.
- The saved-state schema is now `8`. New 1.2 saves no longer encode the legacy player `cue` key, while old state and packages remain readable; 1.2 packages that use the new song model are not intended to import into 1.1.
- Phase 0 policy is now locked in the decision log: local generation is readable-local-only, Apple Music source-backed playback remains a supported normal outcome, downloaded-on-device does not imply portable, and no private API, system-audio capture, DRM bypass, or remote policy switch is planned.

What works now:
- Readable app-owned local audio and readable Music Library files can generate derived `.m4a` playback clips under `Application Support/RollCall/GeneratedClips`
- Generated clips bake the selected duration and fade envelope, retain original source/selection truth, and become the preferred playback recipe when ready
- Apple Music-linked songs without a readable local file stay source-backed; a library item that appears stored on-device can be marked ready here without being marked portable
- Preparation jobs are serialized, deduplicated per player, paused around live use and Low Power Mode, protected by generation keys, and retried no more than twice after the first failure
- Existing saved players and older `.rollcall` packages with legacy `cue` data decode into private player song assignments while preserving the same playback recipe
- New player song edits persist the 1.2 `SongAssignment`/`SongClip` model instead of writing only the legacy cue shape

Known limitations:
- `Recovery` currently uses a simple mixed list with no search or filters, and the new delete/restore flows still deserve a quick on-device smoke pass before treating them as fully field-proven.
- iOS 17.0 is now the checked-in minimum deployment target. The app builds for iOS 17.0, passed the hosted test suite on iOS 17.5 and iOS 18.6 simulators, and launched to the welcome screen on iOS 17.5, but a full hands-on iOS 17 flow smoke is still required before treating this hotfix as App Store-ready.
- A physical iPad running iOS 17 reported Game Day silence after the first batter and one possible Next-button stall. The current hotfix addresses the most likely stale playback-cleanup race, but that exact iPad Game Day flow still needs a repeat smoke test before release confidence.
- Waveforms and per-cue gain remain intentionally deferred.
- Physical-device installs now depend on a valid local Apple development provisioning profile for `com.jkfisher.rollcall`; full-song Apple Music also requires the MusicKit App Service to be enabled for that App ID in Apple Developer.
- Apple Music full-song trimming now depends on a device account state and MusicKit App Service configuration that this environment cannot emulate, so it still needs an on-device feel pass with and without an active Apple Music playback subscription after App ID registration/provisioning refresh.
- The new subscribed-song MediaPlayer backend is implemented but still unproven on a real subscribed device; until that on-device check passes, full-song Apple Music fade behavior should still be treated as provisional.
- The new iOS 18+ `ApplicationMusicPlayer.transition` crossfade path is also still provisional: it compiles and passes the simulator test lane, but it still needs a subscribed on-device feel pass to learn whether Apple actually softens cue endings or only entry-to-entry transitions.
- The new Apple Music hook suggestion is intentionally conservative and still needs an on-device feel pass to judge whether its default entrance guesses are actually helpful.
- Apple Music team playlist creation is promoted in the app, but the actual Apple Music library mutation and unresolved-song recovery path still need a physical-device Apple Music smoke test before release confidence.
- Roll Call now gives only lightweight Focus guidance for interruptions; it still does not have OS-level Do Not Disturb or Guided Access integration.
- In `Announcer Only`, players without a recorded Announcement Cue fall back to `Small Cheer`; in `Announcer+Song`, missing announcers are skipped and missing songs fall back to `Small Cheer`. This fallback is live-safe but does not count as player-specific Ready status in Readiness.
- The no-song Game Day fallback clip is currently code-defaulted to `Small Cheer`; a user-facing selector for changing that default is not implemented yet.
- Local audio import still exists as a fallback path, but it has been moved behind a secondary disclosure in the player editor so Apple Music remains the obvious primary flow.
- Startup and tap responsiveness have been tightened by deferring/coalescing some follow-up work and moving snapshot restore I/O off the main actor, but this still needs an on-device feel pass to confirm the improvement.
